The **`tests/`** folder is responsible for **verification and validation**. Unlike the `models/` folder that performs calculations or the `backend/` that exposes APIs, the `tests/` folder ensures that every component of the Industrial Energy Transition Optimizer behaves correctly under different conditions.

This directly supports the **Validation, Explainability and Trust** principle in your project architecture, where the system must be validated through baseline calculations, infeasible scenarios, sensitivity checks, and reproducible outputs before deployment. 

---

# tests/

## Purpose

The `tests` folder contains automated test cases for validating the correctness, reliability, and stability of the Industrial Energy Transition Optimizer.

Its primary objectives are to:

* verify engineering calculations
* validate optimization results
* detect software bugs
* ensure consistent outputs after code updates
* prevent regressions during development

These tests are executed during development and before deployment to ensure that modifications do not break existing functionality.

* rejects invalid requests

* produces correctly structured JSON responses

# 2. test_baseline.py

## Responsibility

This module verifies the correctness of baseline energy calculations.

It tests whether

* energy demand calculations
* heat demand estimation
* baseline cost
* baseline emissions

match expected engineering values.

---

### Example

Input

```text
Coal = 1000 kg/day
```

Expected

```text
Energy Demand = Calculated Value
```

If the returned value differs significantly,

the test fails.

---

### Why important?

Every optimization begins with the baseline.

An incorrect baseline produces incorrect recommendations.

---

# 3. test_constraints.py

## Responsibility

This file verifies the technical constraint engine.

It checks whether infeasible technologies are correctly rejected.

Typical constraints include

* temperature limits
* grid capacity
* roof area
* biomass availability
* infrastructure compatibility

---

### Example

Factory Requirement

```text
Temperature = 850°C
```

Technology

```text
Solar Thermal

Maximum = 300°C
```

Expected Result

```text
Rejected
```

---

### Why important?

The optimizer should never recommend a technically impossible solution.

# Why a Separate Testing Layer?

The project architecture emphasizes **validation and explainability**. Before presenting a recommendation to the user, every stage—from baseline calculations to optimization and final recommendations—must be verified against known test cases and engineering assumptions. 

Keeping tests in a dedicated folder provides several advantages:

* **Reliability:** Detects errors before deployment.
* **Regression Prevention:** Ensures new code doesn't break existing functionality.
* **Engineering Validation:** Confirms calculations match expected values.
* **Maintainability:** Each module has its own focused test cases.
* **Deployment Confidence:** The application is released only after all tests pass.
