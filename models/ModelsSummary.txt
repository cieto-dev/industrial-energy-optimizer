# Models Folder

## Purpose

The `models` folder contains the **core domain models** responsible for simulating the industrial energy transition process. Every file represents one independent analytical component of the optimization pipeline.

Unlike the UI or API layers, these modules perform the actual calculations, feasibility checks, financial evaluation, emission estimation, and recommendation generation.

The objective of separating these models is to ensure that each responsibility remains modular, reusable, and independently testable.

---

Each model consumes the output of the previous stage and enriches it with additional analysis before forwarding it to the next component.

# 1. industry.py

## Responsibility

This is the **baseline industrial model**.

Its job is to convert raw factory information into an engineering representation that every other module understands.

For example, if the user enters

* Textile Industry
* Coal Boiler
* 12 tons/day production
* 14 operating hours
* 180°C process temperature

the module determines

* current heat demand
* electricity demand
* process temperature requirement
* current fuel consumption
* baseline energy consumption

Instead of repeatedly using raw user inputs throughout the application, every downstream model works with this standardized industrial profile.

---

### Input

```
Factory Information
```

Example

```
Industry
Production
Operating Hours
Fuel Used
Temperature
Location
```

---

### Output

```
IndustryProfile
```

Example

```
{
    heat_demand
    electricity_demand
    baseline_cost
    baseline_emission
    required_temperature
}
```

---

### Why it exists

Every technology comparison must start from the same baseline.

Without this module

Solar Model → uses one calculation

Biomass Model → uses another

Financial Model → uses another

which creates inconsistencies.

# 2. technology.py

## Responsibility

This module represents every alternative technology supported by the platform.

It answers

> **"Can this technology technically satisfy the factory's energy requirement?"**

For every technology it stores

* efficiency
* temperature capability
* operating limitations
* fuel/resource requirement
* installation constraints
* CAPEX assumptions

This corresponds directly to the **Technology Models** layer in the architecture, where each candidate technology is evaluated for capacity, efficiency, temperature capability, resource needs, limitations, and suitability before further decision making. 

---

### Example

Suppose the baseline requires

```
Required Temperature = 550°C
```

Technology database

```
Solar Thermal → 220°C

Electric Boiler → 450°C

Biomass Gasifier → 900°C
```

Result

```
Solar
❌ Not Feasible

Electric Boiler
❌ Not Feasible

Biomass
✔ Feasible
```

---

### Output

A list of feasible technologies

```
[
 Biomass,
 Waste Heat Recovery,
 Energy Efficiency
]
```

## Responsibility

This module estimates the environmental impact of every scenario.

# 6. recommendation.py

## Responsibility

This is the final decision engine.

It receives

* feasible scenarios
* financial analysis
* emission analysis

and ranks every pathway.

Its responsibility is not to calculate engineering values but to determine

> **Which pathway should the industry adopt?**

# Why this architecture?

The separation of these six files follows the natural decision-making pipeline of your Industrial Energy Transition Optimizer:

1. **`industry.py`** establishes the factory's current energy baseline.
2. **`technology.py`** identifies technically feasible technologies.
3. **`scenario.py`** builds realistic combinations of those technologies.
4. **`financial.py`** evaluates the economic viability of each scenario.
5. **`emission.py`** quantifies the environmental impact of each scenario.
6. **`recommendation.py`** ranks all feasible pathways and returns the optimal recommendation.

This modular design ensures that each model has a single responsibility, making the system easier to maintain, validate, and extend. If a new technology (e.g., hydrogen boilers) is introduced later, it primarily affects `technology.py`, while the downstream financial, emission, and recommendation modules continue to operate on the same standardized outputs, keeping the overall architecture stable.
